**神託(原命)**:

## 0. この文書の読み方

**本相は specify である。設計は書かない。** 書くのは「何が満たされれば合格か」だけである。

ただし **受入条件は機械が裁ける形でなければ受入条件ではない**(第10条: 宣言は機構ではない)。
ゆえに本文書の AC はすべて次の型で書かれる:

> **`<コマンド>` が exit `<n>` を返し、`<標準出力/標準エラー>` に `<文字列>` を含む。**

この型が要求するもの — **コマンド名・フラグ名・exit code・出力に含まれる語・閾値の数** — は **要件である。**
その内側(どう実装するか・どのファイルに何を書くか・どんなデータ構造を持つか)は **design の領分であり、本文書は一切触れない。**

呼び出し面や閾値を変えたいなら、design 相は**理由と実測**を添えてこの文書へ差し戻せ。
**黙って別の面を作れば、この文書の AC はすべて空振りする。**

**本文書に根拠の無い数は一つも無い。** 数はすべて (1) findings.md の実測(§番号つきで引用)か、
(2) 本相が実際に走らせたコマンドの出力(§2.4 に全部載せた)である。

## 2. G — 教主の権能は三段の序列である ← **本文書の中核**

### 2.1 序列の定義(神託の訂正をそのまま機構の語彙にする)

| 序列 | 名 | いつ | 証拠となるもの |
|---|---|---|---|
| **序列1** | **委譲** — サブエージェントに為させる | **既定。** 担える役者が居るなら必ずこれ | `spawn-trace` の `observed` 記録(`tool_use.id` / `parent_tool_use_id`) |
| **序列2** | **編成** — オーケストレーションを組む | 作業が **複雑かつ長大**(§2.3 の閾値を超える)とき | forge の DAG + conclave の run。必要なら新しい道と、D の鍛造器による新しい役者 |
| **序列3** | **教主の手** — 教主が自ら行う | **例外。単純かつコンテキスト消費が少ない**(§2.2 の閾値の内側)とき **だけ** | 序列3の宣言 + **事後の実測**(§2.6) |

**序列は下るほど例外である。** 序列1が既定であり、序列3は最後の手段である。
「教主は作業してはならない」ではない。**「教主の手は測られる」である。**

### 2.2 序列3が許される条件 — **測れる量で定義する**

序列3を名乗れるのは、**次の3つをすべて満たすとき、かつそのときに限る**:

| # | 量 | 上限 | **この数の根拠(本相の実測)** |
|---|---|---:|---|
| **T3-a** | その仕事が**触れたファイル数** | **2** | 楽園自身の非merge 113コミットの files/commit 分布で **p25 = 2**。実際の仕事の**下位四分位**を「単純」の上限に採る |
| **T3-b** | その仕事の**変更行数**(added + deleted) | **50** | 同分布の churn は p25 = 106。**106行を「単純」と呼ぶのは無理がある。** 実測の最下位帯 — 113件中 **13件 (11.5%)** が churn ≤ 50 に収まる。ここを上限に採る |
| **T3-c** | 相に紐づく**成果物のバイト数** | **4,096** (4 KiB) | 実在8走行の相成果物 **69件** の bytes 分布で **p25 = 4,040**。これを 4 KiB に丸める。最小は 321B(`verdict@coin`)、中央値は 12,909B |

**T3-a と T3-b を両方課す理由**: 実測で **files ≤ 2 は 40件 (35.4%)**、**churn ≤ 50 は 13件 (11.5%)**、
**両方を満たすのは 11件 (9.7%)** である。片方だけでは「1ファイルに 39,539行」(実測 max)が通る。
**「単純」とは、楽園が実際に行った仕事の下位1割の形をしている、という意味である。**

さらに、**量とは無関係に序列3を禁じる構造的条件**が2つある:

| # | 条件 | **根拠** |
|---|---|---|
| **T3-d** | **門相(`gate: true`)は序列3を名乗れない。** | `forge.js` が自ら gate を宣言している(実測: quick 3 / standard 5 / full 6 / **reform 7** / counsel 4 / cartography 8)。門相とは**判定を下す相**である。教主が自分の仕事を自分で裁けば、それは自己批評の独立を壊す(第9条)。**量が小さくても許さない。** |
| **T3-e** | **序列3は宣言されねばならない。** 宣言の無い手仕事は序列3ではなく、**ただの無証跡である。** | 第27条。事後に「あれは序列3だった」と言えるなら、序列は何も縛らない |

### 2.3 序列2が要求される条件 — 序列1では足りない境界

**「複雑かつ長大」を測れる量にする。** 次の**いずれか**を満たすとき、単発の委譲(序列1)では足りず、序列2が要求される:

| # | 量 | 下限 | **この数の根拠(本相の実測)** |
|---|---|---:|---|
| **T2-a** | 触れるファイル数 | **> 10** | 非merge 113コミットの files/commit で **p75 = 10**(p90 = 14, max = 77)。**上位四分位を超える仕事を「複雑」と呼ぶ** |
| **T2-b** | 変更行数(added + deleted) | **> 880** | 同分布の churn で **p75 = 880**(p90 = 1,692, max = 39,539)。**上位四分位を超える仕事を「長大」と呼ぶ** |
| **T2-c** | 独立して受入判定できる成果物の数 | **≥ 2** | 楽園の**どの道も最低6相**を持つ(実測: quick 6 / counsel 6 / reform 11 / cartography 11 / standard 14 / full 17)。**成果物が2つ以上要る仕事は、既に道の形をしている** |
| **T2-d** | 跨る枢機卿(cardinal)の分野数 | **≥ 2** | `clergy.COLLEGE` は7名の枢機卿で分野を割る(findings §4.1)。**2分野に跨る仕事に単一の神官を当てれば、必ずどちらかが専門外である** |

**閾値を p25 / p75 に採る理由**: 四分位は**楽園自身が実際に行った仕事の分布**から出る。
恣意的な丸め数(「10ファイル」「100行」)ではなく、**この楽園の仕事の形が決めた数**である。
分布が変われば閾値も変わるべきであり、**その再測定は `gauge` の台帳(H)が支える。**

次の行為は**仕事の単位ではなく、環を回す行為である。序列の判定対象にならず、量も測られない。**

| # | 行為 | 具体 |

| G-2 | 契約を検める | `contract.js check` |
| G-3 | 門を撃つ(読み取り専用の engine 実行) | `census check` / `check-agents` / `deploy check` / `atlas check` / `wiring check` / `spawn-trace verify|report|tier|audit` / `gauge score` / `critic review` / `codex` / `node tests/*.test.js` |
| G-4 | 発令書を書く | 神官へ渡す指示文・受入条件・文脈。**命令は成果物ではない** |
| G-5 | 神官の成果物を**読み**、実物とコマンド出力で照合する | 第27条。読むことは作ることではない |
| G-6 | 神と会話する | 神託の受領、報告、確認 |

序列の門は「登録された成果物」だけを見る。ゆえに統治は何も鳴らさない(AC-G1)。

### 2.6 序列は事後に実測される — **自己申告は証拠ではない**(第27条)

**申告(宣言)**:
- 教主は相を `done` にするとき、**その相をどの序列で処理したかを宣言する。**
- 宣言の無い `done` は受理されない(AC-A1)。

**実測(機構が自分で測る)**:
- 対象の窓 = その相の `history` 上の **`dispatch` 時刻 から `done` 時刻まで**(§2.4 で両方の存在を実測済み)。
- その窓の間にリポジトリへ加えられた変更を、**コミット済みの差分と未コミットの差分の両方から**測る。
- 測る量は T3-a(ファイル数)・T3-b(変更行数)・T3-c(成果物バイト数)の3つ。

**突合(門)**:
- **申告と実測が食い違えば鳴る。** これが (c) への回答である。

### 2.8 (d) への回答 — 二つの誤りをどう捕らえるか

**誤り①: 序列3を選んだのに実測が閾値を超えていた。**
門は **exit 1** を返し、標準エラーに次の3つをすべて出す:
1. **超えた量と閾値**(例 `files=7 > 2`, `churn=1420 > 50`, `bytes=58,000 > 4,096`)
2. **本来の序列**(実測が §2.3 の T2 閾値をも超えていれば `序列2`、そうでなければ `序列1`)
3. **委ねるべきだった agent 名**(その相が `forge` の DAG で名指ししている agent。`conclave.json` の `phase.agent` に既に在る — §2.4 で実測)

**「鳴るだけで直せない門は罠である」(第34条)。ゆえに門は次に何をすべきかを言う。**

**誤り②: 序列1が可能だったのに教主が自分でやった(役者が実在したのに)。**
**これは「役者の実在」では捕らえない。閾値で捕らえる。**
理由: 一行の誤字修正のためにサブエージェントを起動させるのは、神託の訂正が明示的に許した例外(序列3)である。
**役者が実在するかどうかは序列3の可否を決めない。決めるのは量である。**
ゆえに誤り②は**誤り①と同じ門が捕らえる** — 役者が居るのに教主が自分でやり、かつそれが単純でなかったときにだけ鳴る。
そして鳴ったとき、門は上の(3)でその役者の名を言う。**「お前が居たのに、教主が 7ファイル・1,420行を自分で書いた」と機構が名指しする。**

**構造的な誤り③: 門相を自分でやった。**
量に関係なく鳴る(T3-d)。第9条(自己批評は独立でなければならない)による。

### 2.9 受入条件(G)

- **AC-G1(統治は偽陽性を出さない)**: 教主の統治行為(§2.5 の G-1〜G-9)が序列の門を鳴らさない。
  `node graph/conclave.js status --run <run> --json`、`node graph/conclave.js next --run <run>`、
  `node graph/contract.js check`(`--run` 無し)、`node graph/census.js check`、`node graph/check-agents.js`
  のいずれも、序列の実装前後で **exit code が変化しない**。
  → 試験: `tests/paradise.test.js` の `第52条: 環を回すことは仕事ではない — 統治は序列の外にある` が passed。

- **AC-G2(序列が機械可読な閾値として1箇所に在る)**: 序列の閾値が engine から読める。
  `node graph/spawn-trace.js tiers --json` が **exit 0** を返し、出力 JSON に
  T3-a(=2)・T3-b(=50)・T3-c(=4096)・T2-a(=10)・T2-b(=880)・T2-c(=2)・T2-d(=2) の**7つの数がすべて現れる**。
  **散文と門が別々に数を持てば必ず食い違う**(第41条: 名の出所は一つ)。

- **AC-G3(`RANKS.pontiff` が序列を持つ)**:
  `node -e "console.log(JSON.stringify(require('./graph/clergy.js').RANKS.pontiff))"` の出力に、
  **三段の序列に対応する構造が現れる**(序列1=委譲 / 序列2=編成 / 序列3=教主の手、およびその順序)。
  現況は `role` 文字列一文のみ(findings §6.3 実測)。
  → 試験名: `第52条: 教主の職務は一文の文字列ではなく三段の序列である`。

## 3. A — 序列の枠を超えた教主の手仕事を捕らえる門

### 3.1 現況(実測)

```

run.spawnTrace after markDone = undefined
spawn-trace.verify(discover) = {"ok":false,"state":"no-trace",...}
```
(findings §2.3)

`markDone` が見るのは `fs.existsSync(artifact)` だけである(`graph/conclave.js:285-296` を本相で確認)。
**教主が自分の手で書いた成果物は当然実在する。** ゆえに門は永久に鳴らない。
**94相のうち、序列を宣言した相は 0 件である**(`spawnTrace` キーを持つ run が 0/8 — findings §2.1)。

### 3.2 四値 — 「観測不能」と「起動していない」を混同しない(第16条)

`spawn-trace.js` は既に三値を持つ(`graph/spawn-trace.js:65-79` を本相で確認):

| 状態 | 意味 | 判定 |
|---|---|---|
| `observed` | `tool_use.id` / `parent_tool_use_id` が在る | 🟢 |
| `asserted-only` | 「起動した」と自称するが id が無い | 🔴 (主張は証拠ではない・第5条) |
| `no-trace` | 証跡が一つも無い | **序列3の宣言と実測次第**(§2.7) |

本件は **第四の状態**を要求する:

| 状態 | 意味 | 判定 |
|---|---|---|
| `unobservable` | **序列と証跡の機構が存在しなかった時代に開かれた走行** | 🟡 **緑ではない。赤でもない。** |

**なぜ第四の状態が要るか。**
第16条は「判定不能は緑ではない」と言う。**「判定不能は赤である」とは言っていない。**
既存8走行94相は「序列を破った」のではなく「**序列を宣言する経路が機構に無かった**」。
この二つを同じ赤で塗れば、機構は **己の欠陥を走行者の罪として記録する。**

### 3.3 移行の判断 — **遡及しない。ただし無かったことにもしない。**

| 選択肢 | 帰結 | 採否 |
|---|---|---|
| (a) 既存 run にも新しい門を適用する | 94/94 が赤。**進行中の本走行(`reform/pontiff-office`)自身が二度と done にできない**。門が仕事を止める | **不採用** |
| (b) 既存 run を免除し、緑として通す | 第16条違反。しかも**新しい run が「既存」を騙れる** | **不採用** |
| (c) 既存 run を `unobservable`(🟡)として通す。新しい run は `unobservable` になれない | 環は回り続け、かつ黄は**増えない**(既存走行が終わるだけ) | **採用** |

**(c) を採る根拠**:
1. **第16条**: 判定不能を緑にしない。黄は緑ではなく、集計でも `observed` にも `序列3` にも数えない。
2. **第34条**(走れない門は落ちる門より悪い): 遡及すれば環が止まる。止まった門は撃たれなくなる。
3. **黄が増えないことを門が裁く**(AC-A7)。これが無ければ (c) は (b) と同じ抜け穴になる。

**legacy か否かの機械的な判定**: run が**序列機構の紀元(epoch)の印**を持つか。
改修後の `conclave.js convene` が作る run は必ず印を持ち、印を持つ run は `unobservable` を名乗れない。
印を手で消せば legacy を騙れるが、**`conclave.json` は版管理下に在るので diff に現れる。**

## 5. C — 役者の居ない仕事が黙って standard へ落ちない門

### 5.1 現況(実測)

15願いのうち **14件(93.3%)** が `standard` へ落ちた(findings §3.1)。

> 名前は全部埋まっているので **門は一切鳴らない。**(findings §3.2)

**agent の実在では足りない。** 必要なのは **分野(domain)の適合**である。

**序列との関係**: 担い手が居ない仕事は、序列1でも序列2でも処理できない。
**そして「音楽を作れ」は §2.2 の閾値の内側に収まらない** — ゆえに序列3でも処理できない。
**この状態を機構が言葉にできないことが、教主が全部自分でやる構造の入口である。**

### 5.2 何が満たされれば合格か(**設計には踏み込まない**)

合格に必要なのは次の4つであり、**それをどう表現するか(frontmatter か台帳か、語彙は何か、判定は語か分類器か)は design が決める。**

1. **役者が「担える分野」を機械可読に宣言している。** 宣言が無い役者は、道に載っていても合格ではない。
2. **願いが分野に写る。** 写せないなら判定不能であり、**判定不能は緑ではない**(第16条)。
3. **道が担えない分野の願いを、道が黙って受けない。** 既定 `standard` への暗黙の転落は禁じられる。
4. **鳴ったとき、次に何をすべきかを門が言う** — D の鍛造器を名指しする(第34条)。

### 5.3 受入条件(C)

- **AC-C1(宣言の網羅)**: 分野の門が、**forge の6本の道が名指しする全 agent** について分野宣言の有無を検め、

  1. 担い手が居ないことを述べる語(例 `担い手が居ない`)

  3. **鍛造器の呼び出し行**(D の engine を名指しする実行可能なコマンド文字列)
  現況は `standard` を出して exit 0(§3.1)。
