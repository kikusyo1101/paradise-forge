## 1. 何が壊れていたか

`gauge.js` の唯一の書き込み経路 `fs.appendFileSync` が**冪等鍵を一つも持たなかった**。
同じ観測を二度撃てば、台帳に二行積まれる。実測:

```
$ node graph/gauge.js ledger --audit      # 実台帳 ../paradise-creations/gauge-ledger.jsonl
📒 rows=30 distinct=6 duplicates=24 conflicts=0
exit=1
```

**30 行のうち 24 行(80%)が同一観測の重複。** 本当に観測されていたのは 6 件だけである。

そこから漏れ出た害:

| 症状 | 実測 |
|---|---|
| `baseline` を走らせるたび台帳が丸ごと増える | 2 行 → 4 行 → 6 行(3 回で 3 倍) |
| `record` の二度打ちも素通り | 6 行 → 8 行 |
| `compare --last 3` の窓が重複で埋まる | 2 創造物しか無いのに `habit / coin / habit` |
| 画面に同じ点が三段並ぶ | `pulse.js` は `readLedger()` の全行をそのまま断面に載せる |
| CI に台帳を検める門が**一つも無かった** | `grep gauge .github/workflows/tribunal.yml` → 空 |

**第38条は「改善は前後の数値で証明せよ」と命じたが、その数値の器が壊れていた。**
台帳が「変化なし」を捏造していたのである。

## 2. どう直したか

### (a) 行は自分の指紋を名乗る

冪等鍵 `fp` は観測の**内容**から決まる:

```
fp = "g1:" + sha256( canonical({ slug, scale, metrics }) ).hex[0..16]
```

- **`ts` は材料に入らない。** 時刻を混ぜれば同じ観測が撃つたび別物になり、冪等性は原理的に成立しない。
- **`fp` 自身も材料に入らない。** これが「鍵を持つ新しい行と、鍵を持たない古い行が同じ鍵になる」ことの成立条件である。
- 素の `JSON.stringify` は使わない — 鍵の並び順に依存し、`metrics` を将来組み直した者が
  黙って指紋を割ってしまう。`canonical()` が鍵を sort し、数を丸め、非有限を `null` にし、
  配列の順序は保つ。
- 接頭辞 `g1:` は**材料と正規化の版**を名乗る。材料を変えるときは `g2:` を名乗り、
  `g1:` の行は `g1:` の規則で読む — 過去の指紋が黙って動く事故を構造で防ぐ。

### (b) 予防と治癒を二重に敷く

```
  書く道                                読む道
  record()                              readLedger()
   1. 指紋を刻む                          1. 破損行は名指して読み飛ばす
   2. 追記前に既存を検め、                 2. 各行の指紋を**再導出**する
      同じ指紋が居れば追記しない            3. 同一指紋は keep-first で畳む
      (既記録を返す。exit 0)              4. ts 昇順に整列して返す
```

片方では足りない。書き側だけでは**既に汚れた帳**と他の枝から流入する重複に無力で、
読み側だけでは台帳が走行回数に比例して膨れ、差分が審査不能になる。
`baseline()` は `record()` の N 重ループなので**一行も変えずに**冪等になった。

### (c) 指紋は判断に使わない — 常に再導出する

**ここが差し戻しで正された最重要点である。** 初版は `e.fp || fingerprint(e)` と書いていた。
つまり行が名乗る鍵を検証せずに採っていた。台帳は人の手で書き換えられる平文の器なので、
**偽の鍵を載せた一行を置くだけで本物の観測が黙って飲み込まれた**
(実測: `score:99` の観測が消え、監査はそれを「重複」としか呼ばなかった)。

いま `trueKey(e)` は**常に中身から導き直す**。格納された `fp` は人が目で読む注記に過ぎず、
畳みにも突き合わせにも監査にも使われない。

> **指紋は同一性の鍵であって、真正性の証明ではない**(第55条(g))。
> `sha256` を用いるのは鍵の衝突を避けるためであり、改竄を検知するためではない。
> 台帳が「改変されていないこと」を保証する仕組みは**この改革には存在しない**。

### (d) 一行の破損で秤全体を倒さない

破損は「`JSON.parse` が通らない行」だけではない。`JSON.parse` は耐えるのに正規化が
`RangeError` で倒れる**深すぎる入れ子**の一行も破損である。
`canonical()` は深さ **64** に底を持ち、越えた行は判別可能な標識で名指されて読み飛ばされる
(実在する `metrics` の深さは 2。64 は現実の 30 倍)。
握り潰して `null` を返しはしない — それでは深い別物どうしが同じ鍵になる。

**しかし「読み飛ばす」は「消す」ではない。** too-deep の行は
**畳みでも掃除でも台帳から消してはならない。**
`foldLedger` は passthrough として素通しし、`--audit` は数えて名指し、
FR-8 の掃除(畳んだ版で置き換える)もその行を残す。
読めなかった行を落とせば、台帳は「読めなかった」という事実ごと失う。

### (e) 「生」を名乗る道は本当に生である

**これが review-2 の差し戻し(P-1)で正された点である。** S-2 の修理は
too-deep の読み飛ばしを `opts.raw` の**前**に置いてしまい、三つの害を産んだ:

1. `readLedger({raw:true})` が行を落とした(ファイル 2 行 → raw 1 行)。監査と掃除の唯一の材料が痩せた。
2. `auditLedger` の too-deep 枝が CLI から**到達不能**になり、
   全行が深すぎる台帳を `--audit` が `rows=0 … exit 0` =「健全」と答えた。
   **読めなかった行を 0 件と数えるのは、測れなかったものをゼロで埋める行為である(第16条)。**
3. FR-8 の掃除が深い行を**ファイルから永久に消す**道になった。

いま **`raw` の分岐は深さの検査より前に返る**。読み飛ばしの判断は最下流(畳み・監査)に住む。

| 口 | 何を返すか |
|---|---|
| `readLedger({ raw: true })` | **ファイルの全行**。破損行(`JSON.parse` 不能)だけを名指して除く。深すぎる行も**返す**。監査・掃除・後方互換の材料 |
| `readLedger()`(既定) | 破損行と深すぎる行を名指して読み飛ばし、同一指紋を keep-first で畳み、`ts` 昇順に整列 |

**`--raw` という CLI の旗は存在しない。** 生はプログラム側の口だけが返す。

### (f) 信号を分ける — exit code は 0 / 1 / 2 / 3

```
$ node graph/gauge.js ledger --audit
```

| exit | 意味 | 誰が直すか |
|---:|---|---|
| **0** | 健全 | — |
| **1** | **機械が畳めば消える欠陥**(重複) | 掃除(FR-8)で必ずゼロにできる |
| **2** | **人が中身を読むまで消えない事故**(偽の指紋 / 深すぎて鍵を導けない行) | 人の手 |
| **3** | 命令・引数の誤り(未知の命令・usage 不足・`--last` が整数でない) | 打った者 |

掃除で消せるものと消せないものを同じ信号に載せれば、(h) が戒める「鳴りっぱなしの門」に再びなる。
`exit 3` は「**何もしなかったことを成功と名乗らない**」ための信号である ——
`gauge.js recrod …`(誤字)が exit 0 を返せば、CI も cron も「記録した」と信じて先へ進む。

実測(仮倉に一行ずつ置いて撃った):

```
偽の fp 1 行   → 📒 rows=1 distinct=1 duplicates=0 conflicts=1 too-deep=0   exit=2
同一観測 2 行  → 📒 rows=2 distinct=1 duplicates=1 conflicts=0 too-deep=0   exit=1
正直な 1 行    → 📒 rows=1 distinct=1 duplicates=0 conflicts=0 too-deep=0   exit=0
深さ 80 の 1 行→ 📒 rows=2 distinct=2 duplicates=0 conflicts=1 too-deep=1   exit=2
                  ⚠️ 読めない行: d — 入れ子が深すぎて鍵を導けない(> 64。畳みでも掃除でも消してはならない)
raw vs 既定    → raw 2 行 / 既定 1 行(生は本当に生である)
```

### (g) 安全の代償を測り、安全を損なわずに返した

「常時再導出」は正しいが只ではない。**測らずに「無視できる」と書くのは第38条の裏返しの違反**
(review-2 P-2)なので、実測して記す:

| 手当て | 実測 |
|---|---|
| `foldLedger` に**呼び出し内 memo**(整列の比較子が O(n log n) 回叩く) | 同一 ts 20000 行 1063ms → 61ms(**x17**) |
| `baseline` が `keyIndex` を一度だけ組む(O(M·N) → O(M+N)) | 台帳 4000 行 × 20 創造物 602ms → 30ms(**x20**) |

**memo も索引も保持するのは「再導出した鍵」であって行の自己申告ではない** —— (c) とは無関係である。
索引はメモリ上にしか住まない: **台帳の第二の住所は作らない**(第30条 / NG-8)。

### (h) 矛盾は畳まない。名指す

同じ `slug` の別の観測(`80 → 100`)は**矛盾ではなく履歴**である。指紋が違うので両方残る。
そこで門を鳴らせば、掃除を終えた台帳が永遠に赤になる「鳴りっぱなしの門」になる。

**名指すべき矛盾は「行が名乗る指紋と、中身から導かれる指紋の食い違い」である** —
指紋は中身の関数なのだから、正直な行では必ず一致する。食い違うのは偽の鍵が生まれた時だけであり、
それが (c) の発火条件そのものである。

### (i) 「最新」は末尾行ではない

git マージ後の台帳の行順は時刻順ではない(実測で `T0, T2, T1` の並びが出た)。
`latestFor` は `ts` の最大を採り、畳みは keep-first(`ts` 最小)を残す。
**行位置を時刻の代理にしない** — それが順序非依存の全てである。

## 3. 何を門で守っているか

`node graph/gauge.js ledger --audit`(読み取り専用)が重複・偽の指紋・鍵を導けない行を数え、
**掃除で消える重複なら exit 1、人が読むまで消えない事故なら exit 2**(§2 (f))。
回帰は `tests/paradise.test.js` の gauge 節が撃つ。

数は手で書かず、実測を引く:

```
$ node tests/paradise.test.js | tail -1
Paradise self-test: 433 passed, 0 failed

$ grep -coE "test\('(gauge|門ヘルパー)" tests/paradise.test.js          → 100
$ git show main:tests/paradise.test.js | grep -coE "test\('(gauge|門ヘルパー)" → 11
$ grep -coE "test\('gauge\(故障注入\)" tests/paradise.test.js           → 9
$ grep -coE "test\('門ヘルパー" tests/paradise.test.js                   → 7
```

| | main | この枝 |
|---|---:|---:|
| 自己試験の総数 | 344 | **433** |
| うち gauge 門(`gauge…` + `門ヘルパー…`) | 11 | **100** |
| うち故障注入門 | 0 | **9** |
| うち**門を守る門**(`門ヘルパー: …`) | 0 | **7** |

門は「実装をなぞる試験」ではない。**故障注入で鳴ることを実測している** —
`gauge(故障注入): …` を名に持つ 9 本が、変異を実際に注入した子プロセスの exit code を見る。

**道が違えば門も違う。** 最後の一本は **CLI を子プロセスで直に叩く** ——
既存の `runGaugeGate` は module を `require` する道なので、
**CLI の引数解釈や exit code を壊す変異は構造的に届かない**。
`--audit` を argv の位置依存にする変異が長らく無音だったのはこれが理由である。

**門ヘルパーを守る門が 7 本ある**(第55条 (i))。
故障注入の門は「壊したら赤くなる」と主張する装置だが、その装置自身
(注入器・走行器・仮倉・素材の生成器)を守る門が無ければ、主張の失効に誰も気づかない。
特に `test()` の集計から `fail++` を落とす変異は、**壊れた集計器の下では全部緑に見える**ので、
門の本文だけを別プロセスで撃って実測している。

守られている主な性質:

- 同じ観測は二度刻まれない(`baseline` 二度・`record` 二度打ち)
- 指紋は `ts` に依存せず、鍵順・`-0`・非有限・丸めに揺れない
- 配列の順序 / object の鍵名 / 真偽値と数の別 が指紋に出る
- `g1:` の値そのものを固定(hash を差し替えれば鳴る)
- 鍵なしの旧行が一つも落ちず、新旧混在が 1 行に畳まれる
- 衝突マーカー入りの台帳でも生きた行が読め、畳みで減らない
- **`raw:true` は本当に生**(深すぎる行も返る)。深すぎる行は畳みで**消されず**素通しされ、
  audit で「重複」と数えられず、掃除でも消えない
- `--audit` の信号は「掃除で消える欠陥」と「人が読むべき事故」を分ける(exit 1 / 2)
- 旗は**位置ではなく存在**で効く(`ledger --json --audit` でも監査する)
- **知らない命令は非ゼロで拒む** — 誤字を成功と呼ばない
- `compare --last` の N は整数のみ、窓は台帳の**末尾** N(「直近」が「最古」に化けない)
- 下流(`pulse`)の断面は畳んだ台帳を載せ、`metrics` なし行で倒れない
- 倉が存在しない機でも `baseline` / `ledger` が落ちない
- 読めない台帳で `record` は黙って「既記録」を名乗らない(fail-open は「書く側に倒す」であって「捨てる」ではない)
- 門自身が仮倉の残骸も `PARADISE_CREATIONS` の振替も残さず、**実台帳を一行も書き換えない**
- 環境変数で畳みや監査を無効化する裏口が無い(設定で消せる門は門の不在に等しい)

## 4. まだ緑になっていないこと(名指して残す)

- **AC-8c(掃除が creations の履歴を書き換えない / 既存 commit の SHA 不変)— 門は無い。**
  これは兄弟倉の git 履歴に対する主張であり、paradise 側の自己診断からは
  兄弟倉の履歴を触らずに検めることができない。
  仮倉に git repo を作って手順を模擬することは原理的に可能だが、**作っていない**。
- **AC-8d(paradise 側の PR に `gauge-ledger.jsonl` が現れない)— 門は無い。**
  PR の diff は自己診断の外にある。`workspace.js check` の `strayRuns` が近い役目を負うが、
  **台帳ファイルが paradise 側の commit に混入することを直に禁じる門は無い。**
  これは CI 側(`.github/workflows/`)に置くべき門である。
- **NFR-3(指紋を CLI から確認できる)— 実装も門も無い。**
  `score --json` は metrics だけを返し `fp` を含まない。
  requirements 自身が nice-to-have と定めているが、「無い」と書かれていなかったのでここで名指す。
- **AC-8a / AC-8b の門は「模擬」であって「実行」ではない。**
  仮倉に実台帳同型の 30 行を置き、`design.md` の掃除手順(`readLedger({raw:true})` →
  `foldLedger` → 書き戻し)をそのまま実演して、30 → 6 行・内訳が V-9 と一致・
  **指紋の集合が前後で完全一致**(観測を一つも失わない)・掃除後に `--audit` が exit 0・
  残るのが各指紋の**最古**の行、を撃つ。
  **保証するのは「手順が正しい」ことであって「実台帳が掃除された」ことではない。**
- **実台帳 30 行 → 6 行の掃除は、この枝では行っていない。**
  台帳の住所は兄弟倉 `../paradise-creations`(第30条)であり、engine の修正とは**別の PR** の領分である。
  ゆえに現在も `ledger --audit` は実台帳に対して非ゼロを返す
  — これは門が正しく鳴っている状態であって、直すべきは台帳の側である。
- **「門は完全です」とは書かない。** 無音がゼロになったのは、その相で打った変異の範囲でだけである。
  次の一つが素通りする可能性は残る —— 実際、三度そうなった(§5)。

## 5. 三度の差し戻しと、その都度の学び

この改革は**三度差し戻されている**。三度とも、prove が「緑」と言った後で別の目が穴を見つけた。
**この履歴そのものが、この改革の最大の産物である。**

| 相 | 自称 | 別の目が見つけたもの | 学び |
|---|---|---|---|
| prove attempt 1(368→**379**門) | 緑 | review が 20 変異 → **8 件無音** / security が S-1(偽の指紋)・S-2(深すぎる入れ子) | **指紋を判断に使ってはならない**。`e.fp \|\| fingerprint(e)` は偽の鍵一つで本物の観測を黙って飲み込む。常に中身から導き直す(第55条 (g)) |
| prove attempt 2(**394**門) | 自ら 25 変異・**無音ゼロ** | review-2 が別の 39 変異 → **14 件無音**。P-1(`raw` が生でない)・P-2(測らぬ性能主張)・P-3(門ヘルパーを守る門が皆無) | **「自分で打った変異が全部鳴った」は何の保証でもない**。上流で黙って行を捨てれば、下流に備えた枝は到達不能な死んだ枝になる(第55条 (h)) |
| build attempt 3(**419**門) | 自ら 12 変異・無音ゼロ | prove-3 が層を変えて 27 変異 → **11 件(41%)無音**。過去約 96 変異はすべて `gauge.js` の**内部ロジック**だけを狙っていた | **同じ層を掘り続ければ穴は見つからない**。CLI の引数解釈・下流の結合・環境依存・境界値・**門自体**は別の層である。道が違えば門も違う |
| prove attempt 3(**433**門) | 27 変異中 11 の穴を塞いだ | — | **無音ゼロを成果として誇らない。** 一巡目に 41% が漏れたという事実のほうが、二巡目に 0% になったという事実より情報量が多い |

もう一つ、**道具自身の欠陥**が二度起きた(`prove-report-3.md` §5.1・§6.2):

- 変異注入器が `tests/paradise.test.js` の復元を `git checkout --` で行っていたため、
  **未 commit の新しい門ごと巻き戻した**。検算が止めて発覚。
- 住所解決を壊す変異(`E1` / `T1`)を注入した状態で門を走らせた瞬間、
  **実台帳が 19 行汚れた**。走行時刻を持つ行を除去して注入前の
  sha256 `387d9e0e…` / 30 行にバイト単位で戻した。
  **「門は実台帳を書き換えない」という保証は、門が正しい実装の上で走る限りでしか成り立たない。**
  次に同じ検査をする者は、注入器を `PARADISE_CREATIONS` 固定の子プロセスに閉じ、
  注入器の側に「実台帳の sha256 を前後で検算する」錠を先に付けよ。
