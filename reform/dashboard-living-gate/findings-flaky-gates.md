# 門が不定に鳴るとき — この改修で三度出会った同じ病

> 一つの reform で **三度**、形を変えて同じ病に出会った。
> 三度目にしてようやく「これは一つの病である」と見えたので、記録する。

## 三つの形

| # | 現れ方 | 症状 | 原因 |
|---|---|---|---|
| 1 | 第21条テストが不定に赤 | 走行ごとに赤/緑が入れ替わる | Chrome 一時プロファイルの漏れ (483→519→529→683) |
| 2 | AC が「壊れていても緑」 | 常に緑。誰も疑わない | `grep -E` の方言違い・`grep -c $'\n\n'` の退化 (5件) |
| 3 | atlas の赤が不定 | **落ちる主題すら回ごとに変わる** | `failAll` の unhandled rejection (**根治済み** — §則Cの実証を見よ) |

## 共通する構造

**症状は揺れる。原因は揺れない。**

1 では、赤が消えた瞬間に「直った」と報告しかけた。だが同時刻に測った
プロファイルは 483 → 519 と**単調に悪化していた**。症状が消えても病は進んでいた。

3 では、前回 dag/hierarchy が落ち、今回 conclave が落ちた。
**どの主題が落ちたかを追えば、永久に真因に辿り着かない。**

## ゆえに立てた則

### 則A: 不定に鳴る門の受入基準は、**症状ではなく原因を数える**

```
✗ AC: node tests/paradise.test.js が 0 failed
      → 漏れが 529 個まで悪化した状態でも緑を出した
✓ AC: 検器を1回走らせる前後でプロファイル数の差が 0
      → 原因そのものを数える。悪化していれば必ず鳴る
```

第22条(数えられる主張)を、**症状ではなく原因に向けて適用する**。

### 則B: 同じ入力で結果が変わったら、**入力の決定性をまず証明する**

```
$ buildIr('conclave',{scale:'reform'}) を2回 → 完全に同一
```

IR が決定的だと証明できて初めて、「揺れているのは下流だ」と言える。
これを先にやらないと、engine を疑って何時間も溶かす。

### 則C: **一つの根が三つの赤を生んでいないか**を先に疑う

自己診断のクラッシュ(15本で停止)・atlas の不定な赤・census の 15 —
別々の欠陥に見えた三つが、`failAll` の unhandled rejection という
一つの根から生えている可能性がある。

**赤を一つずつ潰す前に、根が共通でないかを問え。**
共通なら、一手で三つ消える。一つずつ潰せば、三倍の時間がかかった上に
「なぜか他のも直った」という理解の無い成功が残る。

## 第50条との関係

第50条は「門が見ていない機能は壊れても鳴らない」と述べた。
この改修で、その**三重の形**が揃った:

| 形 | 内容 | 出典 |
|---|---|---|
| 表 | 門が**見ていない** | 第50条 |
| 裏 | 門が**己の残骸で不定に鳴る** | findings-base-red.md |
| 三 | 門の**書き方が誤っていて鳴らない** | findings-gate-syntax.md |
| **四** | **門が不定に鳴り、症状を追うと真因に届かない** | 本文書 |

四つ目は三つ目と似ているが違う。三は「常に緑」で、四は「揺れる」。
**揺れる門は、緑を見たときに「直った」と誤認させる分だけ質が悪い。**

## この改修での実績

- 形1(プロファイル漏れ): **根治済み**。検器1回の前後で差 0 を実測。
  門(motion-probe-leak.test.js)は**原因を数える**形で書かれ、CI に据わった
- 形2(AC の構文): **9件是正済み**。則1〜4 を requirements.md §9 に収録
- 形3(failAll): **根治済み**。下記の通り、則Cが実地で証明された

## 則Cの実証 — 一つの根が三つの赤を生んでいた

真因を特定する前、**三つの別々の欠陥に見えていた**:

| 見えていた症状 | 疑った原因 |
|---|---|
| atlas の赤が不定(落ちる主題が回ごとに変わる) | 図の席割り? 描画器の非決定性? |
| 自己診断が 15本目で止まる(ように見えた) | テストのクラッシュ? |
| `EPERM: rename` で成果物を確定できない | ファイルロック? 権限? |

**すべて `failAll` の unhandled rejection から生えていた。**

```
Error: visual-check finished
  at ChromeVisualBrowser.close (visual-check.mjs:476)
  at probeMotion (graph/motion-probe.mjs:93)
```

`close()` が「正常終了」の合図として `failAll` を呼び、待ち手の居ない Promise を
reject する。Node は既定で unhandled rejection にプロセスを落とす。ゆえに:

- 子プロセスが落ちる → atlas が「動きの検器が走らなかった」と報告(**不定に**)
- Chrome が死にきれない → ファイルを掴んだまま → `EPERM: rename`

### 直した後の実測

```
$ 一時 outdir で conclave を4周
周1: ✓  周2: ✓  周3: ✓  周4: ✓          ← 不定性が消えた
```

**一手で三つ消えた。** 一つずつ潰していたら三倍の時間がかかった上に、
「なぜか他のも直った」という理解の無い成功が残っていた。

### 教主が一度誤った見立てを訂正した記録

途中、教主は「自己診断が15本目でクラッシュしている」と神官に伝えた。**これは誤りだった。**
実測すると自己診断は完走しており(355行出力・276 passed)、「15」の正体は
**census の正規表現が子テストの集計行を先頭で掴んでいた**という**全く別の欠陥**だった。

```
出力中の「N passed, M failed」は 9件あった
  1件目: dashboard-count: 15 passed   ← String.match が拾う
  9件目: Paradise self-test: 276 passed, 1 failed   ← 本当の総括
```

**症状が似ているだけで同根と決めつけた。** 則Cは「根が共通でないか**問え**」であって
「共通だと決めつけよ」ではない。問うたら実測で確かめること — これを則Cに追記する。

### 則C(改訂)

**一つの根が複数の赤を生んでいないかを先に疑え。ただし疑いは実測で確かめよ。**
根が共通なら一手で消える。共通でないのに束ねれば、直したつもりで別の欠陥が残る。
