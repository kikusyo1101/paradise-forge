# design.md — 階層オーケストレーションの再設計

> 神託:「枢機卿はオーケストレーションのコントローラであり、司祭はサブエージェントになり
> 実際の作業を行う。さらに細分化した作業を行う場合はさらに司祭の下に信徒のサブエージェントがいる。
> 階級が高い方から低い方に作業が流れ呼び出されていく。」

`findings.md`（内部実測）と `research-external.md`（外部調査40KB）に基づく。

---

## 1. 何が壊れていたか（一文で）

**楽園は階層を *記述* したが *実行* しなかった。** `clergy.js` は組織を述べるデータ、
`conclave.js` は次に誰が動くべきかを計算する engine。だが
**「計算結果に従って実際に起動する」コードが存在しない**。その空白を教主が埋め、
枢機卿は素通りされ、信徒13名は名前だけの存在になった。

## 2. 調査が決定づけた事実（設計の前提）

外部調査で判明した、設計を変える事実：

| 事実 | 出典 | 設計への影響 |
|---|---|---|
| `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` **既定3層** | Claude Agent SDK docs | **神の3階層は Claude Code 内で実行可能**。諦める必要はなかった |
| `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` 既定20 | 同上 | 幅の上限が明確 |
| `allowedTools` に `Agent`(旧`Task`) が無いと**起動が黙って拒否される** | 同上「これが宣言はあるが起動しない第一原因」 | **司祭に `Task` を与えねば信徒は永遠に呼ばれない** |
| 親→子に渡るのは **Agentツールの prompt 文字列のみ**（親の履歴は渡らない） | 同上 | 発令書に必要な文脈を全部書き込む必要がある |
| 子→親は **最終メッセージのみ**（中間は子に留まる）＝これが context 圧縮の実体 | 同上 | 契約(`contract.js`)で返却形式を強制すべき |
| `description` が曖昧だと**親が自分でやってしまう** | Claude/LangChain/CrewAI 全docs | 起動条件を description に具体的に書く |
| **APIエラーで子が早期終了しても結果として配達されない**（沈黙する失敗） | Claude Agent SDK docs | 「返ってこない」を失敗として扱う機構が要る |
| CrewAI `allow_delegation` **既定 False** | CrewAI source | 権能は明示的に与えるもの |
| 弱いモデルは coworker 名を壊すので `sanitize_agent_name` がある | CrewAI source | 名前解決に正規化と**候補一覧を返すエラー**が必須 |
| マルチエージェントは chat比 **15倍**トークン、性能分散の**80%**をトークン量が説明 | Anthropic engineering | 深さより幅。無闇に階層を深くしない |
| 深さの利得を示す公式データは**見つからなかった** | 調査の正直な記録 | 3階層を上限とし、それ以上を追わない |
| Magentic-One の Progress Ledger: `is_request_satisfied`/`is_in_loop`/`is_progress_being_made` | AutoGen | 停滞判定の具体形として流用する |

## 3. 設計 — 二つの基盤にまたがる階層を、正しく分ける

**重要な発見**: 神の4階層は**二つの異なる実行基盤**にまたがっている。

```
┌─ Hermes セッション ─────────────────────────┐
│  神 → 教主(Pontiff)                          │  max_spawn_depth=1
│         │                                    │
│         │ delegate_task                      │
└─────────┼────────────────────────────────────┘
          ↓
┌─ Claude Code ───────────────────────────────┐
│  枢機卿(Cardinal)  ← Task を持つ唯一の存在    │  MAX_SUBAGENT_SPAWN_DEPTH=3
│         │ Task                                │
│         ↓                                     │
│      司祭(Priest)  ← Task を与える【変更】     │
│         │ Task                                │
│         ↓                                     │
│      信徒(Believer) ← 実体を作る【変更】       │
└──────────────────────────────────────────────┘
```

**教主は枢機卿を起動し、そこから先は Claude Code の中で階層が流れる。**
これなら神の設計「階級が高い方から低い方に作業が流れ呼び出されていく」が
物理的に成立する。

### 3.1 枢機卿を actor にする（最大の変更）

現在 `COLLEGE` は「誰が司祭か」を述べるだけ。ここに**起動の権能と手順**を加える。

- `clergy.js` の各枢機卿に `agent: 'cardinal'` を明示（誰が演じるか）
- `conclave.js next` の返却を **枢機卿への発令書**に変える。
  現在は司祭への発令書を教主に返している。これが素通りの正体。
- 発令書には Anthropic の4点を必ず含める（**目的 / 出力形式 / 使うツールとソース / タスク境界**）

### 3.2 司祭に `Task` を与える

実測で `Task` を持つのは `cardinal` のみ。司祭は信徒を呼べない。
**信徒を使う司祭にだけ** `Task` を与える（最小権限。全員には与えない）。

### 3.3 信徒を実体化する

13名すべてが名前だけ。**実際に使う信徒だけを実体化する**（過剰生成はコスト増）。
Anthropic の「単純クエリに50個の子を生やす」失敗を繰り返さない。

### 3.4 検査の門（第21条の拡張）

`check-agents.js` は司祭しか見ていない。**信徒も名指しの対象**なので検査に含める。
加えて：
- **権能の検査**: 信徒を持つ司祭が `Task` を持っているか（無ければ黙って起動しない）
- **深さの検査**: 宣言した階層が `MAX_SUBAGENT_SPAWN_DEPTH` を超えていないか

### 3.5 停滞・沈黙の検知（Progress Ledger）

「APIエラーは結果として配達されない」= 沈黙する失敗が実在する。
`contract.js` を拡張し、**返ってこない/空/未完了マーク**を明示的な失敗として扱う。

## 4. この変更で嘘になる既存の門（第23条 design 相の義務）

構造を変えるので、古い前提を符号化した門を洗い直す：

| 門 | 現在の前提 | 変更後 | 対応 |
|---|---|---|---|
| `check-agents.js` | 司祭のみ検査 | 信徒も名指し対象になる | **拡張**（信徒＋権能＋深さ） |
| `clergy.js marshal` | 信徒は司祭が兼務する前提 | 信徒は実体を持つ | 返却に実在性を反映 |
| `conclave.js next` | 司祭への発令書を教主に返す | 枢機卿への発令書 | **変更**（level を明示） |
| テスト「believers は名前だけでよい」 | 存在しない | — | 新規に実在性テストを追加 |

---

## 5. 意図的にやらないこと（範囲の宣言）

- **4階層以上にしない。** 深さの利得を示す公式データは見つからなかった。既定3が目安
- **13名すべての信徒を実体化しない。** 実際に呼ばれるものだけ。過剰生成はトークン15倍の世界で害
- **本 reform では Claude Code 側の実起動テストまでは行わない。**
  engine と門の整備が範囲。実起動の検証は次の神託に譲る（正直な範囲宣言）
